# Agent-based modelling of spatial co-occurrence and cholera exposure under urban decentralisation

Python and Slurm implementation of a spatially explicit agent-based cholera
model for Douala, Cameroon. Four controlled synthetic spatial arrangements
are compared: **Baseline**, **POI redistribution**, **WASH redistribution**,
and **POI+WASH redistribution**. The analysis separates mapped proximity,
realised facility use and experienced exposure. It is not calibrated to
forecast a historical outbreak or to recommend real facility sites.

## Repository structure

- `code/douala_model.py` — model and scenario definitions
- `code/ensemble_runner.py` — precomputation, stochastic simulation jobs and aggregation
- `code/postprocess.py` — statistics and main/supplementary figure workflow
- `code/render_publication_figures.py` — Figure 4(a–c) and Figure 6(a–b), with publication-scale annotations
- `code/render_figure6_maps.py` — Figure 6(c–f), using light-background maps, amber generic-POI shading, blue E+I density, shared scales and small facility symbols
- `code/prepare_population.py` — convert the external WorldPop GeoTIFF into the input CSV
- `code/check_outputs.py`, `code/check_figures.py`, `code/preflight.py` — data, figure and environment checks
- `code/validate_overture_baseline.py` — independent Overture Maps spatial validation
- `slurm/` — dependency-ordered batch jobs; `submit_douala_pipeline.sh` submits them
- `environment/`, `configs/`, `inputs/` — environment specification and external input guidance

The two named figure renderers are **part of the normal postprocessing stage**,
not alternative models or scripts requiring an archived dataset. They use the
outputs generated by the current run.

## Run from the beginning on Leeds Aire

The scripts expect Linux, Slurm's `nodes` partition, Miniforge 24.7.1,
a Python 3.11 Conda environment called `airenotebook`, and project directory
`/mnt/scratch/$USER/cholera_project`. The `environment/environment.yml` file
records the packages used for the study; environment creation may need
adjustment on another system.

1. Clone the repository into your Aire project directory. The commands below
   assume the project is named `cholera_project` on Leeds Aire:

   ```bash
   mkdir -p /mnt/scratch/$USER/cholera_project
   cd /mnt/scratch/$USER/cholera_project
   git clone https://github.com/parna1997/douala-cholera-spatial-model.git
   module load miniforge/24.7.1
   ```

   **Conda:** If the `airenotebook` environment does not already exist, create
   it from `douala-cholera-spatial-model/environment/environment.yml` before
   running `conda activate`:

   ```bash
   conda env create -f douala-cholera-spatial-model/environment/environment.yml
   conda activate airenotebook
   ```

   On systems where this machine-specific environment export cannot be solved
   directly, create a Python 3.11 environment and install the packages listed
   in the environment file; the exact software versions are documented in
   Supplementary Table S4. A full new-system/clean-environment installation
   has not been independently verified.

2. Download the WorldPop 2020 Cameroon unconstrained 30 arc-second raster
   described in [`inputs/README.md`](inputs/README.md).
3. Supply the population raster and generate its point/weight CSV:

   ```bash
   PROJECT_ROOT=/mnt/scratch/$USER/cholera_project
   cd "$PROJECT_ROOT"
   mkdir -p "$PROJECT_ROOT/inputs/douala/data" "$PROJECT_ROOT/configs"
   cp douala-cholera-spatial-model/configs/cities.example.csv "$PROJECT_ROOT/configs/cities.csv"
   cp /path/to/downloaded/WorldPop_Cameroon_2020.tif "$PROJECT_ROOT/inputs/douala/data/pop.tif"
   python douala-cholera-spatial-model/code/prepare_population.py \
     --raster "$PROJECT_ROOT/inputs/douala/data/pop.tif" \
     --csv "$PROJECT_ROOT/inputs/douala/data/pop.csv"
   ```

   The `cp` source above is an **example filename**; use the actual downloaded
   GeoTIFF filename. See the input guidance for details.
4. Install the source files and launch the pipeline:

   ```bash
   bash douala-cholera-spatial-model/install_to_aire.sh
   cd "$PROJECT_ROOT"
   bash submit_douala_pipeline.sh
   ```

The stages check the environment and input files, prepare the spatial layout,
execute **50 independent seeds (42–91) for each of four scenarios** (200 runs),
aggregate the checkpoints, compute statistics and generate figures, perform
an independent Overture validation, and package the results. A fresh run may
need internet access for OpenStreetMap downloads during spatial precomputation.
The separate Overture job also needs access to the public Overture data services;
if that service is unavailable, the independent validation/packaging stage may
fail even though the simulations and journal-style figures have completed.
Job monitoring:

```bash
squeue -u "$USER"
sacct -j JOB_ID --format=JobID,State,ExitCode,Elapsed
```

Use an **empty** `outputs/douala/run_3000/` directory for a new run. The number
`3000` is only a run-directory identifier; it does not refer to any private or
historically stored simulation. Existing outputs are not overwritten by the
installation script, and you should not mix checkpoints from different runs.

## Running outside Leeds Aire

**Access to Leeds Aire is not required to use the model.** The repository contains
Python model, analysis and figure-generation code; the supplied job scripts are
an **Aire-specific Slurm reference workflow**. They are **not** a turnkey
cross-platform installer. In particular, the job scripts specify Aire's
`nodes` partition and Miniforge module, and default to Aire's scratch path.
The exact environment and external input snapshots used for the article are not
included. A complete fresh run on an alternative cluster or workstation has
not been independently tested.

### Other Linux HPC clusters using Slurm

1. Clone the repository and create a **writable project/work directory**. You
   need the external inputs described in `inputs/README.md` and a compatible
   Python 3.11 environment. The captured `environment/environment.yml` is a
   Linux environment record, not a guaranteed portable lockfile. Use the
   versions in Supplementary Table S4 as a reference if dependencies need
   adapting.
2. Prepare `configs/cities.csv` and `inputs/douala/data/pop.tif` and
   `pop.csv` following the Aire example above, but replace the scratch path
   with your own. Set `PROJECT_ROOT` to that directory before installation:

   ```bash
   export PROJECT_ROOT="$HOME/cholera_project"  # replace with suitable scratch/work path
   mkdir -p "$PROJECT_ROOT/inputs/douala/data" "$PROJECT_ROOT/configs"
   # Prepare population files and cities.csv as documented above.
   bash douala-cholera-spatial-model/install_to_aire.sh
   ```

   Despite its historical name, `install_to_aire.sh` only copies the code and
   Slurm scripts to `$PROJECT_ROOT` after checking the required inputs.
3. **Before submitting jobs**, edit the installed `slurm/*.sh` scripts:
   change `#SBATCH --partition=nodes` to the partition available on your
   cluster (or remove it if your cluster has a suitable default); adjust
   requested memory, CPUs, wall times and array concurrency to its limits;
   and replace `module load miniforge/24.7.1` / `conda activate airenotebook`
   with your site's supported environment activation. For example, if Conda
   is installed in a known location, a batch job can use
   `source /your/conda/path/etc/profile.d/conda.sh` followed by
   `conda activate YOUR_ENV`.
4. Export `PROJECT_ROOT` in the submitting shell, then run
   `bash "$PROJECT_ROOT/submit_douala_pipeline.sh"`. The normal stages create
   the required checkpoints and render the final Figures 4 and 6 **from that
   new run**. Check the job logs; a new-system environment may need additional
   site-specific changes before completing.

### Linux workstation or cloud VM without Slurm

The same Python stages can in principle be invoked **sequentially**, without
`sbatch`. This is a resource-intensive research model (the reference Slurm
jobs request up to 64 GB memory and use 200 stochastic scenario runs), so an
ordinary laptop may not have sufficient resources. The instructions below
mirror the Slurm pipeline but are **not a tested one-command local release**.
Work in the prepared project directory, with `code/`, `configs/` and
`inputs/douala/data/` already installed or copied there, and activate a
compatible Python environment first.

```bash
export PROJECT_ROOT="$PWD"
export PYTHONUNBUFFERED=1
export RUN_SOBOL=0 RUN_PARAMETER_SCREENING=0 RUN_MOBILITY_COMPARATOR_MAIN=0
export RUN_COOCCURRENCE_ENSEMBLE=1 COOCCURRENCE_RESUME=1
export RUN_PAPER_PLOTS=0 RUN_DIAGNOSTIC_PLOTS=0 KEEP_LEGACY_PLOTS=1

# 1. Prepare/cache the urban environment.
python code/ensemble_runner.py --model-source code/douala_model.py \
  --city_slug douala --run_id 3000 --mode precompute

# 2. Generate 50 seeds (42 to 91) across all four scenarios.
#    Run sequentially here; a workstation can parallelise cautiously if resourced.
for seed in $(seq 42 91); do
  export COOCCURRENCE_N_SEEDS=1 COOCCURRENCE_SEED_START="$seed"
  python code/ensemble_runner.py --model-source code/douala_model.py \
    --city_slug douala --run_id 3000 --mode worker || exit 1
done

# 3. Verify/aggregate the completed run.
export COOCCURRENCE_N_SEEDS=50 COOCCURRENCE_SEED_START=42
python code/check_outputs.py --project-root "$PROJECT_ROOT" \
  --city_slug douala --run_id 3000 --seed-start 42 --n-seeds 50 \
  --checkpoint-version 7 --write-report || exit 1
python code/ensemble_runner.py --model-source code/douala_model.py \
  --city_slug douala --run_id 3000 --mode aggregate --model-plots || exit 1
python code/check_outputs.py --project-root "$PROJECT_ROOT" \
  --city_slug douala --run_id 3000 --seed-start 42 --n-seeds 50 \
  --checkpoint-version 7 --require-aggregate-csvs --write-report || exit 1

# 4. Statistics and final manuscript-style figures.
python code/postprocess.py --project-root "$PROJECT_ROOT" \
  --city_slug douala --run_id 3000 --seed-start 42 --n-seeds 50 \
  --bootstrap-resamples 10000 --permutations 10000 || exit 1
python code/check_figures.py --project-root "$PROJECT_ROOT" \
  --city_slug douala --run_id 3000 --min-width-px 3000
```

The optional, independently downloaded **Overture validation** is separate and
can be run when network access and the relevant Overture release are available:

```bash
python code/validate_overture_baseline.py \
  --project-root "$PROJECT_ROOT" --city_slug douala --run_id 3000 \
  --release latest
```

The local sequence does not automatically produce the Aire-specific
`environment/` provenance report or final `.tgz` archive; those are recorded
by the Slurm stages. The **publication figures** themselves are created by
`postprocess.py` and written to the same `figures/publication/` directory
listed below. Do not mix outputs/checkpoints from different runs.

## Final journal-style figures

The normal `slurm/04_postprocess_douala.sh` stage automatically produces the
final figures from the **newly generated** run in:

```text
outputs/douala/run_3000/cooccurrence_ensemble/figures/publication/
    Figure4a.png / Figure4a.pdf
    Figure4b.png / Figure4b.pdf
    Figure4c.png / Figure4c.pdf
    Figure6a.png / Figure6a.pdf
    Figure6b.png / Figure6b.pdf
    Figure6c.png / Figure6c.pdf
    Figure6d.png / Figure6d.pdf
    Figure6e.png / Figure6e.pdf
    Figure6f.png / Figure6f.pdf
    Figure6_legend.png / Figure6_legend.pdf
    Figure6_colorbar.png / Figure6_colorbar.pdf
```

Figure 4 heatmaps use the same four scenarios, font sizes, colour contrast and
mean±SD annotations. Figure 6(c–f) maps display a shared nonlinear blue E+I
scale and a separate amber generic-POI density overlay; the same plotting
parameters are applied across scenarios. The underlying values are taken from
the outputs of the *new* simulation, not manually entered or supplied from a
past run. **For the final Figure 4 and Figure 6 as styled in the article, always use
`figures/publication/`.** The internal `figures/main/` folder contains
additional analytic/legacy figure series with different numbering and, in some
cases, older styling. Do not substitute these internal numbered plots for the
`Figure4*` and `Figure6*` files in `figures/publication/`.

The postprocessing stage also creates other main and supplementary
analysis figures in `figures/main/` and `figures/supplement/`.

### Re-render without rerunning simulations

After finishing a run, you can regenerate the journal Figure 4 and Figure
6(a–b) files from its aggregate CSVs:

```bash
python code/render_publication_figures.py \
  --csv-dir outputs/douala/run_3000/cooccurrence_ensemble \
  --out outputs/douala/run_3000/cooccurrence_ensemble/figures/publication
```

Regenerate the light Figure 6(c–f) maps from that run's *own* checkpoint arrays
and scenario layouts:

```bash
python code/render_figure6_maps.py \
  --run-dir outputs/douala/run_3000/cooccurrence_ensemble \
  --out-dir outputs/douala/run_3000/cooccurrence_ensemble/figures/main
```

The second command writes the map filename stems (`fig6C`, etc.) to
`figures/main/`. To refresh all final manuscript filename aliases in
`figures/publication/`, rerun the full postprocessing stage on the completed
ensemble; it copies those maps there without rerunning simulations.
Keep the `checkpoints/` directory if you may want to redraw spatial maps later.
The compressed results archive intentionally excludes these large files.

## External data and numerical reproducibility

- The **agent-based simulation uses WorldPop and OpenStreetMap**, plus synthetic
  facilities, households and agents. It does **not** consume Overture Maps.
- The Overture Maps assessment is a separate spatial plausibility check. The
  article used release `2026-08-19.0`; the validation program can resolve the
  latest available release, record its version, and produce newer validation
  statistics. Changing the Overture release alone does not change Figures 4/6.
- A fresh download of OpenStreetMap, or a different population raster,
  environment or simulation settings, can change city geometry and numeric
  results. **The plotting pipeline preserves the figure design but does not
  guarantee identical values to the accepted article** without identical input
  snapshots and computational conditions.
- Original simulation outputs, heavy checkpoints, externally obtained raster
  data and the original OpenStreetMap snapshot are not redistributed here.

The manuscript and supplementary material document the model assumptions,
parameter values, scenario definitions and limitations.
