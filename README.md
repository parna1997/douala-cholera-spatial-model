# Agent-based modelling of spatial co-occurrence and cholera exposure under urban decentralisation

Python and Slurm implementation of a spatially explicit agent-based cholera
model for Douala, Cameroon. Four controlled synthetic spatial arrangements
are compared: **Baseline**, **POI redistribution**, **WASH redistribution**,
and **POI+WASH redistribution**. The analysis separates mapped proximity,
realised facility use and experienced exposure. It is not calibrated to
forecast a historical outbreak or to recommend real facility sites.

## Repository structure

- `code/douala_model.py` — model and scenario definitions
- `code/ensemble_runner.py` — precomputation, stochastic simulation jobs and aggregation
- `code/postprocess.py` — statistics and main/supplementary figure workflow
- `code/render_publication_figures.py` — Figure 4(a–c) and Figure 6(a–b), with publication-scale annotations
- `code/render_figure6_maps.py` — Figure 6(c–f), using light-background maps, amber generic-POI shading, blue E+I density, shared scales and small facility symbols
- `code/prepare_population.py` — convert the external WorldPop GeoTIFF into the input CSV
- `code/check_outputs.py`, `code/check_figures.py`, `code/preflight.py` — data, figure and environment checks
- `code/validate_overture_baseline.py` — independent Overture Maps spatial validation
- `slurm/` — dependency-ordered batch jobs; `submit_douala_pipeline.sh` submits them
- `environment/`, `configs/`, `inputs/` — environment specification and external input guidance

The two named figure renderers are **part of the normal postprocessing stage**,
not alternative models or scripts requiring an archived dataset. They use the
outputs generated by the current run.

## Run from the beginning on Leeds Aire

The scripts expect Linux, Slurm's `nodes` partition, Miniforge 24.7.1,
a Python 3.11 Conda environment called `airenotebook`, and project directory
`/mnt/scratch/$USER/cholera_project`. The `environment/environment.yml` file
records the packages used for the study; environment creation may need
adjustment on another system.

1. Download the WorldPop 2020 Cameroon unconstrained 30 arc-second raster
   described in [`inputs/README.md`](inputs/README.md).
2. Put the downloaded `douala-cholera-spatial-model` folder **inside**
   `/mnt/scratch/$USER/cholera_project`, activate the `airenotebook` Conda
   environment, supply the population raster and generate the point/weight CSV:

   ```bash
   PROJECT_ROOT=/mnt/scratch/$USER/cholera_project
   cd "$PROJECT_ROOT"
   module load miniforge/24.7.1
   conda activate airenotebook
   mkdir -p "$PROJECT_ROOT/inputs/douala/data" "$PROJECT_ROOT/configs"
   cp douala-cholera-spatial-model/configs/cities.example.csv "$PROJECT_ROOT/configs/cities.csv"
   cp /path/to/downloaded/WorldPop_Cameroon_2020.tif "$PROJECT_ROOT/inputs/douala/data/pop.tif"
   python douala-cholera-spatial-model/code/prepare_population.py \
     --raster "$PROJECT_ROOT/inputs/douala/data/pop.tif" \
     --csv "$PROJECT_ROOT/inputs/douala/data/pop.csv"
   ```

   The `cp` source above is an **example filename**; use the actual downloaded
   GeoTIFF filename. See the input guidance for details.
3. Install the source files and launch the pipeline:

   ```bash
   bash douala-cholera-spatial-model/install_to_aire.sh
   cd "$PROJECT_ROOT"
   bash submit_douala_pipeline.sh
   ```

The stages check the environment and input files, prepare the spatial layout,
execute **50 independent seeds (42–91) for each of four scenarios** (200 runs),
aggregate the checkpoints, compute statistics and generate figures, perform
an independent Overture validation, and package the results. Job monitoring:

```bash
squeue -u "$USER"
sacct -j JOB_ID --format=JobID,State,ExitCode,Elapsed
```

Use an **empty** `outputs/douala/run_3000/` directory for a new run. The number
`3000` is only a run-directory identifier; it does not refer to any private or
historically stored simulation. Existing outputs are not overwritten by the
installation script, and you should not mix checkpoints from different runs.

## Final journal-style figures

The normal `slurm/04_postprocess_douala.sh` stage automatically produces the
final figures from the **newly generated** run in:

```text
outputs/douala/run_3000/cooccurrence_ensemble/figures/publication/
    Figure4a.png / Figure4a.pdf
    Figure4b.png / Figure4b.pdf
    Figure4c.png / Figure4c.pdf
    Figure6a.png / Figure6a.pdf
    Figure6b.png / Figure6b.pdf
    Figure6c.png / Figure6c.pdf
    Figure6d.png / Figure6d.pdf
    Figure6e.png / Figure6e.pdf
    Figure6f.png / Figure6f.pdf
    Figure6_legend.png / Figure6_legend.pdf
    Figure6_colorbar.png / Figure6_colorbar.pdf
```

Figure 4 heatmaps use the same four scenarios, font sizes, colour contrast and
mean±SD annotations. Figure 6(c–f) maps display a shared nonlinear blue E+I
scale and a separate amber generic-POI density overlay; the same plotting
parameters are applied across scenarios. The underlying values are taken from
the outputs of the *new* simulation, not manually entered or supplied from a
past run. The postprocessing stage also creates other main and supplementary
analysis figures in `figures/main/` and `figures/supplement/`.

### Re-render without rerunning simulations

After finishing a run, you can regenerate the journal Figure 4 and Figure
6(a–b) files from its aggregate CSVs:

```bash
python code/render_publication_figures.py \
  --csv-dir outputs/douala/run_3000/cooccurrence_ensemble \
  --out outputs/douala/run_3000/cooccurrence_ensemble/figures/publication
```

Regenerate the light Figure 6(c–f) maps from that run's *own* checkpoint arrays
and scenario layouts:

```bash
python code/render_figure6_maps.py \
  --run-dir outputs/douala/run_3000/cooccurrence_ensemble \
  --out-dir outputs/douala/run_3000/cooccurrence_ensemble/figures/main
```

The second command writes the map filename stems (`fig6C`, etc.) to
`figures/main/`. To refresh all final manuscript filename aliases in
`figures/publication/`, rerun the full postprocessing stage on the completed
ensemble; it copies those maps there without rerunning simulations.
Keep the `checkpoints/` directory if you may want to redraw spatial maps later.
The compressed results archive intentionally excludes these large files.

## External data and numerical reproducibility

- The **agent-based simulation uses WorldPop and OpenStreetMap**, plus synthetic
  facilities, households and agents. It does **not** consume Overture Maps.
- The Overture Maps assessment is a separate spatial plausibility check. The
  article used release `2026-08-19.0`; the validation program can resolve the
  latest available release, record its version, and produce newer validation
  statistics. Changing the Overture release alone does not change Figures 4/6.
- A fresh download of OpenStreetMap, or a different population raster,
  environment or simulation settings, can change city geometry and numeric
  results. **The plotting pipeline preserves the figure design but does not
  guarantee identical values to the accepted article** without identical input
  snapshots and computational conditions.
- Original simulation outputs, heavy checkpoints, externally obtained raster
  data and the original OpenStreetMap snapshot are not redistributed here.

The manuscript and supplementary material document the model assumptions,
parameter values, scenario definitions and limitations.
